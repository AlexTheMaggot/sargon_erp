# Модули и права доступа

Актуализация: 2026-10-09. Источники: `api/views.py`, `api/consumers.py`,
миграции, `constants/navigation.js`, `components/App/App.jsx`, страницы управления.

## Публичные подсказки входа

`GET /api/auth/login-options/` намеренно доступен до авторизации: он возвращает
только логины активных пользователей, без ID, имён, контактов, групп и прав.
Это согласованное раскрытие существующих активных логинов любому посетителю
страницы входа; его нельзя считать защитой от перечисления учётных записей.
Отключённые пользователи исключены. Ответ запрещает кеширование, но это не
скрывает список от посетителя. API `access/users/` остаётся защищённым, а наличие
логина в подсказках не заменяет проверку пароля и активности при аутентификации.

## Модель

У пользователя не более одной группы через `UserProfile.group`.
У группы несколько модулей через `GroupModuleAccess`; у каждой такой связи
свой набор `Permission`. Название роли не выбирает права автоматически,
за исключением специальной проверки группы `Администраторы`.

Неактивный модуль исключается из карты доступа обычного пользователя.
Важная совместимость: привязка группы к модулю без выбранных разрешений
трактуется `_user_access_map()` как `view`, а не как полное отсутствие доступа.
Для снятия доступа необходимо убрать модуль, а не только очистить права.

## Администраторы: две разные проверки

| Проверка | Кто проходит | Где используется |
| --- | --- | --- |
| `_has_permission()` | Superuser безусловно; остальные — по группе и модулю | Общие API доступа, приёма, лаборатории, справочников |
| `_is_admin()` | Superuser, staff либо член группы с точным именем `Администраторы` | Доменные исключения, переработка, склад, база знаний |

`is_admin` в ответе о пользователе позволяет фронтенду показывать административные
страницы. Это не универсальный обход всех серверных `_require_permission()`.
Staff/член административной группы может видеть страницу, но не иметь API-права,
если соответствующая привязка отсутствует. Не подменяйте это различие предположением
«любой администратор всегда имеет доступ ко всему».

## Матрица модулей

Пути — страницы React. Для обычного пользователя открытие защищённой страницы
требует `view`; действие дополнительно проверяется сервером.

| Код | Страница / область | Рабочие права и ограничения |
| --- | --- | --- |
| `dashboard` | `/welcome` | Сейчас обзор и его API доступны любому аутентифицированному пользователю; `view` участвует в выборе стартовой страницы, но не ограничивает обзор |
| `access` | `/access/users`, `/access/groups`, `/access/modules`, `/access/permissions` | Стандартные `view`, `create`, `update`, `delete`; также управление городами |
| `suppliers` | `/directories/suppliers` | Стандартный CRUD; API принимает также соответствующее право `access` |
| `raw-material-receiving` | `/raw-material/receipts` | `view`, `create`, `update`, `delete`; завершение — `update`, добавление партии — `create` |
| `laboratory-analysis` | `/laboratory/analyses` | `view`, `update`, `approve`; для решения нужны и `update`, и `approve`; ручное создание/независимое удаление запрещены |
| `used-oil-processing` | Страницы ёмкостей в «Прочее» | `view` даёт список; изменение/создание/удаление ёмкостей требует `_is_admin()`, одних CRUD-прав недостаточно |
| `boiler-loading` | `/processing/boiler-loading` | `view` для формы, `create` для движения бак → котёл |
| `separator-loading` | `/processing/separator-loading` | `view`, `create`: котёл → сепаратор |
| `separator-output` | `/processing/separator-output` | `view`, `create`: вода/мусор из сепаратора |
| `chemical-mixer-loading` | `/processing/chemical-mixer-loading` | `view`, `create`: сепаратор → химмиксер |
| `workshop-loading` | `/processing/workshop-loading` | `view`, `create`: химмиксер → цех |
| `raw-diesel-tank-loading` | `/processing/raw-diesel-tank-loading` | `view`, `create`: цех → бак сырой солярки |
| `raw-spindle-tank-loading` | `/processing/raw-spindle-tank-loading` | `view`, `create`: цех → бак сырой веретенки |
| `warehouse-accounting` | `/warehouse/overview`, `/warehouse/receipts`, `/warehouse/issues`, `/warehouse/transfers`, `/warehouse/inventory` | `view`, `receipt`, `issue`, `transfer`, `transfer-confirm`, `inventory` |
| `warehouse-settings` | `/warehouse/settings/items`, `/warehouse/settings/categories`, `/warehouse/settings/units`, `/warehouse/settings/warehouses` | Стандартный CRUD либо `_is_admin()` |
| `knowledge-base` | `/knowledge` | Стандартный CRUD либо `_is_admin()` |

Стандартный CRUD означает: GET → `view`, POST → `create`, PATCH/PUT → `update`,
DELETE → `delete`, если endpoint поддерживает этот метод. Назначение права само
по себе не создаёт отсутствующий метод или новый маршрут.

## Специальные зависимости

### Города и поставщики

- Страница городов `/directories/cities` защищена модулем `access`.
- API чтения городов допускает `access:view`, `suppliers:view` или
  `raw-material-receiving:view`, чтобы формы могли выбирать город.
- Изменение городов требует соответствующего CRUD-права `access`.
- Чтение поставщиков через самостоятельный справочник требует
  `suppliers:view` либо `access:view`. Менеджеру приёма нужно учитывать эту зависимость
  при настройке группы, иначе выбор поставщика не получает список через этот API.
- Складское `warehouse/reference-data/` самостоятельно предоставляет поставщиков
  с правом `warehouse-accounting:view`, без выдачи права их редактировать.

### Ёмкости для одной формы

Оператор с `view` одной формы получает API-списки необходимых ёмкостей,
но не полномочия менять их справочник:

| Форма | Доступные типы для выбора |
| --- | --- |
| Загрузка котла | Приёмные баки, котлы |
| Загрузка сепаратора | Котлы, сепараторы |
| Отгрузка сепаратора | Сепараторы |
| Загрузка химмиксера | Сепараторы, химмиксеры |
| Загрузка цеха | Химмиксеры, цеха |
| Загрузка сырой солярки | Цеха, баки сырой солярки |
| Загрузка сырой веретенки | Цеха, баки сырой веретенки |

Менеджер приёма отдельно читает активные приёмные баки для распределения;
`?purpose=receipt` выдаёт сокращённые данные, включая свободный объём.

### Административные операции

Журнал `/processing/journal`, компенсации, запись в справочники производственных
ёмкостей и отмена складских документов требуют `_is_admin()`. Отдельного права
`cancel` для склада сейчас нет. Изменение количества распределённой партии
и её анализа запрещено даже администратору.

## Складские разрешения

| Право внутри `warehouse-accounting` | Что разрешает |
| --- | --- |
| `view` | Просмотр остатков, всех складов, документов и данных выбора |
| `receipt` | Создание/проведение поступления, удаление его черновика |
| `issue` | Создание/проведение внутреннего расхода, удаление его черновика |
| `transfer` | Создание/отправка перемещения, удаление его черновика |
| `transfer-confirm` | Подтверждение либо отказ по перемещению «В пути» |
| `inventory` | Создание/проведение инвентаризации, удаление её черновика |

Для работы через UI выдавайте `view` вместе с нужными операционными правами.
Это один модуль с разными разрешениями, не отдельный модуль на каждую форму склада.
Меню показывает складские страницы по `view` всего модуля; кнопки действий зависят
от конкретного права. Только администратор проводит другой датой и отменяет документы.

## Стартовая страница

Фронтенд после входа использует серверный `user.start_path`. Сервер:

1. Для superuser выбирает `/welcome`.
2. Для пользователя без группы — `/welcome`.
3. Использует `group.start_module`, если модуль активен, имеет `default_path`
   и есть `view` в карте доступа группы.
4. Иначе выбирает обзор при `dashboard:view`.
5. Иначе — первый по имени активный модуль с явно назначенным `view` и непустым путём.
6. Если такого нет — `/welcome`.

Проверка настройки стартового модуля требует его связи с группой; активность,
путь и разрешение проверяются при выборе старта. Пустые разрешения дают `view`
в карте доступа, но не совпадают с SQL-условием явно назначенного `view` на шаге 5.

Создание модуля в CRUD не создаёт страницу React. Его `default_path` должен
указывать на реализованный маршрут; при добавлении нового маршрута синхронизируйте
бэкенд, seed, навигацию, `ProtectedRoute` и описание прав.

## Начальные группы и миграции

Это стартовые настройки, не результат текущего запроса к БД:

- `Менеджер приема сырья`: CRUD приёма, позднее CRUD поставщиков, старт приёма.
- `Лаборант`: `view`, `update`, `approve` лаборатории, старт лаборатории.
- `Администраторы`: права, создаваемые соответствующими seed-миграциями,
  и доменные исключения по имени группы.
- `0027` перенёс права старого `used-oil-processing` на отдельные формы;
  старые группы могут сохранить широкий доступ, пока его явно не ограничат.
- `0029` добавил складские модули административной группе.
- `0031` добавил существующим группам чтение базы знаний, административной — CRUD.
  Новые группы после этой миграции требуют явной настройки.

Нельзя говорить, что лаборант видит буквально только одну страницу: обзор доступен
всем вошедшим, а существующая группа получила базу знаний. Это не даёт ему право
на операции приёма или другие формы переработки.

## WebSocket

Подключение требует `view` в `raw-material-receiving` либо `laboratory-analysis`.
Consumer строит карту по группе, без отдельного bypass superuser/staff;
администратору без нужной связи может быть отказано в сокете при доступном HTTP API.
`target_module` дополнительно ограничивает адресованные события.

Права читаются при подключении. При проверке изменённых групп отдельно проверяйте
повторный вход/загрузку данных пользователя и переподключение сокета.
