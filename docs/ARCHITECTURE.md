# Архитектура

Актуализация: 2026-11-06. Описана текущая локальная реализация, не целевая архитектура.

## Компоненты

```text
React + React Router
  ├─ HTTP JSON /api/ → Django views → PostgreSQL
  └─ WebSocket /ws/operations/ → Django Channels

Локально: Vite проксирует HTTP и WebSocket на бэкенд.
Развёртывание: отдельная сборка фронтенда и существующие серверные сервисы.
```

- Django 6, без Django REST Framework. Ответы API формируются через `JsonResponse`.
- PyJWT: JWT доступа с HS256; ключ — `settings.SECRET_KEY` из окружения.
- PostgreSQL: модели, ограничения целостности, транзакции и блокировки строк.
- Channels/Daphne: ASGI и уведомления операций приёма/лаборатории.
- React 19, JavaScript/JSX, React Router, Vite 8. Бренд — SHENOLL;
  технические имена `sargon_erp` и ключ `sargon_access_token` сохраняются.

не используются; API, JWT, маршруты, групповые стартовые страницы и WebSocket
не изменяются. Собственных кнопок, подсказок или обработчиков событий установки

Нет отдельного сервисного слоя для доменных операций: сейчас логика находится
в функциях `views.py`. Не описывайте желаемое разделение как уже реализованное.

## Связи данных

### Доступ и справочники

```text
User 1 → 1 UserProfile → 0..1 AccessGroup
AccessGroup ↔ Module через GroupModuleAccess
GroupModuleAccess ↔ Permission
AccessGroup → 0..1 start_module (Module)

City 1 → N Supplier
Supplier 1 → N RawMaterialReceipt
```

Профиль создаётся сигналом при сохранении пользователя. Пользователь может быть
без группы. Прямой связи пользователя с модулями нет.

Обзор проверяет `dashboard:view` и на клиенте, и на сервере; доменные администраторы
обходят эту проверку. Старт остаётся настройкой группы. При отсутствии доступных
разделов используется `/no-access`; отказ в маршруте не отправляет всех на обзор.
У начальника смены сохранены производственные формы, но нет обзора/административных
полномочий; старт — рабочее место производства. Миграция `0043` сохраняет старый доступ к обзору
прочих существующих групп явными привязками, не назначает новый административный статус.

`productionWorkspace.js` — общий каталог 21 производственной операции для старого
меню и новых карточек. `/production` показывает три направления: переработка масла,
производство масла, канистры/крышки; категории показывают только разрешённые формы.
Это навигационная страница, не производственная сводка и не новый API данных.
`ProductionWorkspacePage`, `ProductionIcon`, `ProductionBreadcrumbs` сохраняют
существующие адреса форм и серверные проверки. `production-workspace:view`
включает компактное меню для неадминистратора и может стать стартом любой группы;
миграция `0044` первоначально назначает его только начальнику смены.

### Приём и производство

```text
RawMaterialReceipt 1 → N ReceiptBatch 1 → 1 LaboratoryAnalysis
ReceiptBatch → N MaterialMovement → ProductionContainer
ProductionContainer → N входящих/исходящих MaterialMovement
MaterialMovement → 0..1 компенсируемое MaterialMovement
```

- Старое nullable-поле `LaboratoryAnalysis.receipt` сохранено для совместимости;
  новые анализы привязываются к партии через `batch`.
- `ProductionContainer.kind` различает пятнадцать видов ёмкостей. Общая модель не означает
  взаимозаменяемость типов: каждый маршрут проверяет источник и назначение.
- Баланс хранится в `current_volume_liters`; история — в `MaterialMovement`.
- `api/oil_processing.py` реализует общую линию сорбция → финишный миксер → фильтр
  → раздельные готовые баки. `oil_product` фиксирует продукт в непустом общем
  оборудовании и снимок продукта движения. PostgreSQL transaction-level advisory
  lock `734092601` сериализует операции линии и компенсации, включая пустую линию.
  Блокировки ёмкостей берутся по PK, изменение их вместимости также блокирует строку.
- История хранит пользователя, время, объём, связи и текстовые снимки названий,
  остатки до/после, ключ идемпотентности и сведения о компенсации.
- `OperationAuditLog` отдельно хранит действия и некоторые отклонённые операции.
  Это не универсальный аудит всех изменений всех сущностей.

### Производство товарных масел

`api/oil_manufacturing.py` связывает готовую веретенку, складской полипропилен,
реакторы концентрата, блендинговые смесители, продуктовые баки и розлив.
`OilGrade` — динамический справочник марок; `OilManufacturingBatch` хранит
загрузку оборудования, измеренные переливы, статус, автора и даты. Одновременно
в единице оборудования может быть только одна открытая партия (DB constraint).
Движения имеют `source_oil_batch` / `destination_oil_batch` и снимок марки.

Литры основы и кг полипропилена не складываются. У реакторов/смесителей точный
остаток смеси не выводится из загрузки: `current_volume_liters` технически равен
нулю и в API отдаётся как `null` с `volume_known: false`. Вместо него UI показывает
загруженные жидкие компоненты и суммарный фактический выход при переливах.
Вместимость ограничивает загрузку и суммарный измеренный выход одной партии.
Продуктовые баки хранят реальный литровый остаток и обязательный FK марки.

Загрузка реактора создаёт складской расход `production_target=oil_concentrate`
с единичным списанием полипропилена; отменить его отдельно от партии нельзя.
Создание партии, складское списание и жидкостные движения атомарны. Для операций,
завершения, компенсаций и отмен используется тот же PostgreSQL advisory lock,
что и для финишной очистки. Присадки, учёт тары и складской приход фасованного
масла не подключены по текущему решению пользователя.

### Независимый склад

```text
InventoryCategory / UnitOfMeasure → InventoryItem
InventoryItem N ↔ N Warehouse (permanent_warehouses)
Warehouse + InventoryItem → WarehouseBalance (уникальная пара)
WarehouseDocument → N WarehouseDocumentLine → InventoryItem
WarehouseDocument → N WarehouseMovement → Warehouse + InventoryItem
WarehouseDocumentSequence → номер по типу документа и году
```

Склад не связан с производственными балансами автоматически. Поставщики общие.
Средняя стоимость хранится по паре склад/номенклатура; последняя закупочная цена —
в карточке номенклатуры.

`InventoryItem.production_material` определяет назначение гранул, красителей,
сорбента и полипропилена; `permanent_warehouses` задаёт постоянное отображение позиций с нулевым
остатком без создания строк баланса при GET. Имена товаров не управляют логикой.
Загрузка в производство — специализация `WarehouseDocument` типа `issue` с
`production_target` и уникальным `idempotency_key`, не параллельная система остатков.
Стоимость берётся из неизменяемых `WarehouseMovement`. Три формы используют
общие `ProductionLoadingPage` и `useProductionLoading` с опросом раз в 15 секунд.
Сырьё на участке вычисляется по проведённым загрузкам минус активный расход
в `ProductionMaterialUsage`. Отдельного кеша остатков производства нет.
`ProductionOutput` хранит регистрацию выпуска, автора, дату, ключ запроса и отмену;
`ProductionOutputLine` — изделие, результат (годные/отклонение/брак) и штуки.
Расход связан с исходным `WarehouseMovement`, количество и стоимость сохранены.
Блокировка исходных складских документов сериализует выпуск и отмену загрузок;
разные выпуски не могут расходовать одни и те же остатки сверх доступного.
Формы `ProductionOutputPage` используют общий `useProductionLoading` с режимом
`outputs`. Автоматическое оприходование изделий и себестоимость единицы продукции
отложены: текущая стоимость относится к фактически использованному сырью.

### Замкнутый контур сорбента

`api/sorbent.py` учитывает массу в общем производственном баке, сорбент-системах
и на прогреве/очистке. Бак — единое логическое место хранения, не новая жидкостная
ёмкость с вместимостью в литрах. Источниками служат проведённые складские расходы
на `sorption`; исторические неотменённые выдачи тоже считаются пополнениями бака.
`SorbentMovement` ссылается на исходный `WarehouseMovement` и конкретную
`ProductionContainer` вида `sorption_system`. Остатки по исходной выдаче вычисляются
из неизменяемых движений; компенсированные движения исключаются. Это связь с
документом происхождения, не новая система складских партий.

Операции: `tank_to_system` → `system_to_regeneration` → `regeneration_to_tank`.
Компенсация — отдельная строка с уникальным `reversal_of`, не удаление исходной.
Движения, компенсации, отмена складских документов и изменение ёмкостей используют
общий advisory lock масляной линии, затем блокировки строк. GET не создаёт остатков.
`GET/POST /api/processing/sorbent-cycle/` возвращает справочные данные, остатки и
историю; POST `/<id>/reverse/` доступен только администратору.
`SorbentCyclePage` и `useSorbentCycle` обновляют данные каждые 15 секунд и при фокусе.
Общий обзор получает только количества через `sorbent_cycle`, без финансовых полей.

### Схема канистр и крышек

На «Обзоре» третья вкладка «Производство канистр» содержит обе линии на одной
странице. Гранулы представлены обычной входной карточкой в каждой линии без
визуального обозначения общего запаса. После выдачи сырья остатки каждой линии
раздельны, поэтому у входных карточек разные идентификаторы.
Отдельного верхнего блока общих гранул и нижнего пояснения о браке нет.
Красители представлены отдельными позициями. У канистр три выхода: годные, отдельная складская позиция
с отклонениями и брак. У крышек только годные и брак. В каждой линии только брак
связан с измельчением и возвратом в своё вторсырьё; между контурами нет связей.
Сырьё и результат измельчения обозначены в кг, готовая продукция и брак до
измельчения — в штуках. Пересчёт штук в килограммы не выполняется.

Сырьё и зарегистрированный выпуск подключены к `packaging_production` в API
обзора. Сводка содержит только количества, не стоимость или список товаров.
Килограммы — остаток сырья на участке; штуки — накопленный выпуск без отмен,
не остатки склада. Вторсырьё/измельчение пока статичны и помечены как схема.
Карточки открывают существующее модальное окно этапа.
Линии и идентификаторы узлов описаны отдельно для последующего подключения API,
а переводы находятся в `frontend/src/i18n/canisterProduction.js`.

### База знаний

`KnowledgeCategory 1 → N KnowledgeArticle`. У статьи есть заголовок, краткое описание,
текст, автор, последний редактор и даты. Удаление используемого раздела защищено.
Статьи — обычный текст с ограниченным форматированием, не произвольный HTML.

## Локализация интерфейса

- `frontend/src/i18n/core.js` содержит выбор `ru`/`uz`, перевод обычных строк
  и шаблонов, форматы локали и уведомление подписчиков. Русский — язык по умолчанию,
  узбекский использует латиницу. `useLanguage()` подписывает React на изменения.
- `LanguageSwitcher` доступен до и после входа. Выбор хранится в `shenoll_language`
  и синхронизируется событием `storage`; атрибут языка HTML обновляется.
  На странице входа используется `variant="flags"`: две кнопки с локальными SVG
  флагами России и Узбекистана, без видимого текста; выбранная кнопка отмечена
  визуально и через `aria-pressed`, названия языков доступны скринридеру.
  В шапке после входа сохранён стандартный селект с подписью.
  Смена языка не перезагружает страницу и не меняет JWT, маршруты или права.
- `uz.js`, `ru.js`, `serverMessages.js`, `systemMessages.js` содержат переводы
  интерфейса, известных ошибок и системных обозначений. Исходные сообщения API
  и значения в БД не изменяются. Новую ошибку API нужно добавить в словарь.
- `localizeStaticData()` предназначена только для статичных конфигураций схем
  и форм. Пользовательские названия, комментарии и значения полей остаются исходными.
- `knowledgeGuides.js` содержит переводы начальных инструкций. `knowledge.js`
  применяет их только при точном совпадении исходных заголовка и содержимого.
  При изменении статьи показывается авторский текст; редактор всегда сохраняет
  исходные данные, не перевод представления. Страница базы знаний загружается
  отдельно, чтобы инструкции не увеличивали начальную загрузку остальных экранов.
- Даты и числа отображаются через `getLocale()` (`ru-RU`/`uz-Latn-UZ`). Единицы
  переводятся только в подписях; числовой смысл и единицы хранения не меняются.

| Производство масел | `oil-production/operations/{concentrate-loading,oil-blending,oil-tank-loading,oil-filling}/`: GET — справочные данные/история, POST — проведение |
| Партии масел | `oil-production/batches/<id>/{complete,cancel}/`: POST; отмена только администратором |
| Оборудование масел | `oil-production/containers/{concentrate-reactors,oil-blenders,finished-oil-tanks}/`: GET/POST; общий `processing/containers/<id>/` для изменения и удаления |

| История и компенсация | `processing/journal/`, `processing/movements/<id>/compensate/` |

| Складские справочники | `warehouse/settings/categories/`, `units/`, `items/`, `warehouses/` — все под `warehouse/settings/` |

| Складские действия | `warehouse/documents/<id>/post/`, `transfer-decision/`, `cancel/` — под тем же документом |
| Загрузки материалов | `warehouse/production-loadings/<target>/` — список/проведение; `reference-data/` — разрешённые материалы, склады и доступное количество; target: `canisters`, `caps`, `sorption` |
| Выпуск упаковки | `warehouse/production-outputs/<target>/`, `reference-data/`, `<id>/cancel/`; target: `canisters`, `caps` |

Большинство списков возвращает весь разрешённый набор; фронтенд ищет подстроку
без учёта регистра и делит его на страницы по 10. Это не серверная пагинация.
Журнал производственных операций имеет серверные фильтры и пагинацию, но
формирует объединённый список до разбиения на страницы.

## Авторизация и безопасность транспорта

- HTTP использует `Authorization: Bearer <JWT>`; фронтенд хранит JWT в `localStorage`.
- Вход возвращает токен и пользователя с `access`, `is_admin`, `start_path`.
- Поле логина связано с нативным `datalist`: при открытии страницы входа
  `GET /api/auth/login-options/` без авторизации возвращает весь отсортированный
  список логинов активных пользователей (`items`: массив строк). Другие поля
  пользователя не выдаются. Список хранится только в состоянии страницы, не
  в `localStorage`; ответ имеет `Cache-Control: no-store`, запрос — `cache: no-store`.
  История успешных входов больше не используется. Ошибка загрузки не мешает
  ручному вводу и входу; создание/отключение пользователя отражается после
  повторного открытия или перезагрузки страницы входа.
- `/auth/me/` используется при восстановлении сессии. Refresh-токенов и серверного
  отзыва токена при выходе сейчас нет: выход удаляет локальное состояние.
- Не обещайте немедленный отзыв уже выданного JWT при смене пароля/отключении
  пользователя: отдельного механизма отзыва здесь нет, проверку активности при
  декодировании надо учитывать в отдельном аудите.
- Скрытое меню не является защитой API; детали прав — в [ACCESS_CONTROL.md](ACCESS_CONTROL.md).

## Синхронизация

| Экран | Текущее обновление |
| --- | --- |
| Приём и лаборатория | Событие WebSocket и повторная загрузка HTTP; резервный опрос каждые 15 секунд |
| Обзор производства | HTTP-опрос каждые 15 секунд |
| Формы переработки | Загрузка при открытии и после собственного действия |
| Складские документы | Загрузка при открытии и после собственного действия |
| Складские остатки | При открытии, возврате фокуса и опрос раз в 15 секунд |
| База знаний | Загрузка при открытии и обновление локального состояния после собственного CRUD |

WebSocket: `/ws/operations/?token=<JWT>`. События содержат тип и идентификаторы;
авторитетные данные клиент перечитывает через HTTP. `receipt_created` и
`batch_created` вызывают звуковое уведомление на странице лаборатории. Звук зависит
от разрешённого браузером воспроизведения после взаимодействия пользователя.

`InMemoryChannelLayer` работает внутри одного процесса, а не между несколькими
worker-процессами. WebSocket проверяет доступ при подключении; не считайте смену
прав мгновенным переподключением существующего сокета. Не сохраняйте JWT из URL
сокета в диагностических отчётах или логах.

## Целостность, время и миграции

- Производственные распределения/перемещения и складские проведения используют
  транзакции и блокировки. Не все обычные CRUD-цепочки заключены в одну транзакцию;
  нельзя распространять гарантии защищённых движений на все endpoints.
- `Decimal` используется для доменных количеств и стоимости; значения сериализуются
  строками. В UI форматирование и мягкие предупреждения могут использовать `Number`.
- `USE_TZ=True`, локальный пояс `Asia/Samarkand`. Отбор «сегодня» использует локальную дату.
- Есть squash-миграция `0001_squashed_0016_seed_used_oil_processing`, заменяющая
  `0001`–`0016`; исходные миграции оставлены. Не удаляйте их и не меняйте применённые
  миграции без отдельной проверки истории всех окружений.
- `0027` выделяет формы переработки, `0028`/`0029` добавляют склад,
  `0030`/`0031` — базу знаний. Номер последней миграции не доказывает её применение
  на внешнем сервере.

## Развёртывание

Существующий workflow запускается на push в `main` и вручную, использует self-hosted
runner. `scripts/deploy.sh` блокирует параллельный запуск, синхронизирует исходники,
устанавливает зависимости, собирает React, выполняет миграции, `collectstatic`,
`check`, перезапускает приложение и перечитывает Nginx.

Сохраняются production `.env`, медиа, виртуальное окружение и каталоги зависимостей/
сборки. Текущий скрипт не является резервным копированием БД или автоматическим
откатом миграций. Конфигурация конкретного сервера не проверялась при документации.
